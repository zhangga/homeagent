# 已取消事项误路由与冷启动校验修复（2026-11-05）

## 问题与修复

真实复测中，新的独立调研请求因标题相同，被路由到已经取消的旧事项。输入一直处于 `waiting`，没有创建 Run；另一条周报请求在 Run 创建前等待约 45.5 秒，实际调度等待仅 158 毫秒。两条请求没有并行执行。

路由现在区分独立新请求与明确续接：独立新请求不会按标题挂到已停用或已完成的历史事项；存在同名活动事项时优先匹配活动事项。回复、飞书话题根消息和已展示事项编号仍优先决定归属，同一事项／话题仍顺序执行。

运行时还会修复旧版留下的误路由：仅限在明确取消之后收到、没有 Run、没有冻结执行或路由计划、重新判断属于独立新请求的等待输入。修复使用原有持久化接口，失败后可重试，重启后不会重复创建 Run；取消前的输入、暂停事项的续接、明确回复和已有执行计划不会被自动恢复。本次只读检查确认，此前卡住的真实调研输入符合这一条件；没有手工改写真实数据目录。

冷启动采样测得完整技能校验约 **76.1 秒**，其中一个包含已安装依赖的技能包占 **63.4 秒**。另一轮 CPU 采样中 `readFileSync` 占 79.4%，散列计算不足 1%；单独改变排序方式没有解释这段耗时。预热只能把等待提前，不能消除逐文件串行读取的成本。

目录 Worker 和技能副本 Worker 现共用完整包校验实现，包内最多同时读取 16 个文件。目录请求仍按顺序处理，相邻请求共用解析结果，避免重复冷扫描。同步兼容入口与异步入口共享原有 v1 摘要算法；完整技能、资源、脚本、已安装依赖和已有容量边界全部保留。读前检查路径，读后核对文件身份；失败时等待在途读取结束再清理。

## 验收方法

在 Windows 创建全新进程与隔离数据目录，关闭测试预热，读取本机 116 个技能并加入 2 个离线测试技能。真实 Engine、Orchestrator、Worker、调度器和本地子进程参与执行，模型和飞书投递使用替身。首批同时发送两条独立请求，并预置一个已取消的同名调研事项。外部进程持续请求 `/work` 和 `/healthz`。

这里的冷启动指新进程没有应用内目录缓存；没有清空操作系统文件缓存。结果反映本机测量，不代表任意磁盘或系统负载下的时延保证，也不等于真实模型首个 token 的耗时。
